# 架构与开发组织

状态：建议实施基线，尚未在用户项目中实现。日期：2026-10-18。

## 两层协作

开发层由 Codex 主控分派任务、创建子线程和工作树、审查并集成代码。
应用层是一个可追踪的营销工作流：固定职责、明确数据、可停止和重试，关键语义节点调用大模型。

这样可以同时控制开发冲突与参赛输出的可靠性。应用不需要依赖开发时的 Codex 会话才能运行。

## 默认技术选择

- 单 Git 仓库、单套依赖；TypeScript，Next.js App Router，服务端使用 Node.js runtime。
- 页面与接口在同一应用；ima 官方 CJS 调用封装在服务端 Adapter。避免把底层响应泄漏到业务模块。
- 模型服务通过一个清楚的接口隔离；第一版只接实际可用的一个提供商，并把 endpoint/model 设为服务端配置。
- 首版使用本地持久运行记录与受控资产缓存，建议放 .local-data/；单实例开发即可。运行记录含 runId、修订号、事实、核验和来源。公开部署如无法持久落盘，再由主控根据平台实际能力调整。
- 不预先引入微服务、消息队列、向量库或另一个 Agent 编排框架。已有合适项目栈可以沿用，理由写入 DECISIONS.md。
- 依赖版本由阶段一核实当前官方要求并锁定。不能因为 ima 脚本最低支持 Node 18，就断言整个应用也只需要 Node 18。

Next.js 的 Route Handlers 可承载服务端 HTTP 接口；环境变量的客户端公开规则必须按官方文档处理。ima 与模型密钥不使用 NEXT_PUBLIC_ 前缀。
参考：https://nextjs.org/docs/app/getting-started/route-handlers
参考：https://nextjs.org/docs/app/guides/environment-variables

## 应用内部数据流

1. 解析 TaskBrief，确定用户、人群、场景、型号、目标和平台；必要时返回澄清问题。
2. 生成 ContentStrategy，给出卖点优先级与理由。候选卖点还不是可发布事实。
3. ima Adapter 定位指定库，检索型号，必要时按目录回退；读取实际原文及图片。
4. 形成 ProductEvidence 与 ImageAsset，只纳入可证事实和可核对型号的图片。
5. 根据事实包与平台规则生成结构化图文，不给模型秘密或任意联网补事实能力。
6. 核验每项产品陈述、图片、引用、平台要求和营销风险；冲突或缺口进入需要确认状态。
7. 核验通过的修订才能复制或导出；修改请求创建新修订并重新核验。

详细字段与状态见 CONTRACTS.md。开发中先确定内部接口，再冻结。内部接口可以保持稳定，ima 原始响应差异由 Adapter 处理。

## 目录与依赖方向

| 目录 | 职责 |
| --- | --- |
| src/contracts/ | 输入、策略、证据、图片、运行状态及校验结构的唯一来源 |
| src/server/ima/ | 官方接口、分页、目录回退、错误归一化、来源提取 |
| src/server/llm/ | 唯一模型服务适配接口及结构化输出解析 |
| src/server/workflow/ | 流程状态、任务修订、策略与生成编排 |
| src/server/verification/ | 产品事实、图片、平台与风险核验 |
| src/server/assets/ | 私有原件获取与前端受控图片预览，不接受任意外部 URL |
| src/server/runs/ | 运行记录、修订和受控导出 |
| src/app/api/ | 对外应用接口，统一输入验证、错误和秘密边界 |
| src/app/、src/components/、src/styles/ | 任务输入、策略与证据、图文成稿、核验和修改界面 |
| prompts/runtime/ | 实际被业务流程加载的系统提示词，纳入版本记录 |
| tests/ima/、tests/workflow/、tests/ui/ | 与上述职责对应的针对性检查 |
| .local-data/ | 忽略的真实原始内容与运行缓存 |
| fixtures/synthetic/ | 可提交的人工构造样例，必须带模式标记 |

客户端可以引用安全的 contracts 类型，不能导入 server 的凭证、raw response 或访问头。证据可展示必要短摘录、来源标题及定位；完整原文和受限访问方式留服务端，展示遵守赛事权限。

初版建议有连接状态、开始任务、查看任务、修改任务、受控图片与导出这几类接口。精确路径及字段由主控在数据契约版本 v1 中冻结，不由各 worker 各写一套。

## 阶段一：主控先打通关键依赖

主控检查现有项目并初始化可运行基础；可同时派两个只读子任务分别检查 ima 材料与赛题覆盖。主控随后完成最小只读探测、证据记录和数据契约冻结。

第一关是实际拿到一份原文和一张型号有依据的图片。一张图片仅用于验证接入，不等于满足正式公众号或小红书图数要求。

没有凭证时继续完成项目基础、错误分类、合成样例与接口结构，但将真实接入标为 BLOCKED，契约标为暂定。不得以假数据通过接入关。

## 阶段二：三个实现任务并行

只在共享数据契约与基础依赖有可引用提交后创建工作树：

| Worker | 负责 | 不负责 |
| --- | --- | --- |
| ima_engineer | 检索、分页、目录回退、来源包与相关检查 | UI、业务文案、共享数据契约、根依赖 |
| workflow_engineer | 场景策略、模型、生成、核验、修订与相关检查 | 改动 ima 原始协议、页面、根依赖 |
| ui_engineer | 表单、策略/来源/图文/核验呈现、修改与导出交互 | 服务端秘密、业务接口实现、共享数据契约 |

主控负责共享数据契约、HTTP 路由、资产与运行存储以及集成。子任务发现数据契约不足时给出精确提案；主控更新数据契约后通知受影响任务，不让它们各自兼容一个不同的版本。

## Git 协作规则

同一 checkout 同时一个写入者。三名 worker 的独立工作树由主控管理，建议放在仓库内被忽略的 .worktrees/，使用互不重复的分支名。先有干净基础提交，才能建立工作树。

示意命令（由主控检查路径和分支后执行，不要求用户手工执行）：

    git worktree add -b codex/s2-ima .worktrees/s2-ima HEAD
    git worktree add -b codex/s2-workflow .worktrees/s2-workflow HEAD
    git worktree add -b codex/s2-ui .worktrees/s2-ui HEAD

对子线程明确工作树绝对路径与基准提交，并再次核对。工作树不自动复制被忽略的凭证和缓存；使用授权的进程环境或本机配置，不能把秘密提交到 Git。

Worker 返回 commit、允许范围内的 diff 和实际验证。主控逐一审查并 cherry-pick，避免重叠 Git 操作。以主控 checkout 的集成结果作为最终实现，完成后按授权清理无用工作树，保留需要的提交记录。

如果当前环境不允许建立工作树，先完成可并行只读任务，实现任务顺序运行；不回退为多人同时改同一 checkout。

## 阶段三：新上下文独立验收

新主对话读取仓库与运行证据，先检查当前真实完成度，再在稳定提交上派最多三个只读评审任务。评审可以按来源与事实、策略与输出、运行与凭证边界分工。不要让评审自行改代码与实现者竞写。

主控处理确认的缺陷，针对修改重跑相关验证，完成 ACCEPTANCE.md 要求的真实案例与视频。最终说明书明确已实现、受限和未验证能力，不把设想写成产品功能。
