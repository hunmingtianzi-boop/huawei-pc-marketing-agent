# 华为 PC 营销软文智能体：产品与实现范围

状态：三平台核心应用已实现，接入1.0.0保留、业务2.1.0支持local来源。用户本轮明确授权从本机知识库原文和图片读取，不走ima API；以下仅ima来源要求在本机交付模式下改为授权local来源，型号/事实/核验标准不变。实际验收及正式赛事未完成项以STATUS为准。

## 1. 要交付的东西

做一个门店导购和内容运营能够使用的图文软文工作台：用户给出产品、人群、场景和平台，系统补齐关键需求，从指定 ima 共享知识库读取产品事实和图片，自行形成内容策略、生成图文、逐项核验，然后提供可复制或导出的成稿。

ima 是事实与素材来源。场景判断、平台策略、提示词、内容组织、事实及图片核验由本项目实现。允许调用公开大模型服务，不要求训练基础模型；仅转发 ima 生成的最终文章不满足赛题的自研要求。[R1，第 3、5、8 页]

### 首版范围

| 项目 | 首版要求 |
| --- | --- |
| 产品 | 可由用户指定知识库内的具体产品，并能换型号；不把单一型号的固定结果当作完整产品能力 |
| 人群与场景 | 至少覆盖两类业务场景；优先做好开学购机与出差办公，门店到访用于短文案演示 |
| 平台 | 公众号、小红书、门店朋友圈 |
| 结果 | 场景判断、知识库依据、图文软文、核验结果四部分 |
| 修改 | 删减、换平台、换场景、替换卖点后，更新内容并重新核验 |
| 导出 | 复制最终文本、导出文本或 Markdown；保留图片说明、来源和建议插入位置 |
| 图片 | 真实来自 ima，型号适用范围可证，能在评审环境中受控展示；不引入外部图或生成图补数量 |
| 后续项目 | 门店海报单独列为次级待做；直播脚本、自动发布、CRM、复杂营销分析不属于首版承诺 |

平台图片数量按赛题执行：公众号 2–4 张、小红书 3–6 张、门店朋友圈 1–3 张。海报的 1 张主视觉要求供后续实现使用，不能据此声称首版已覆盖海报。[R1，第 4 页]

## 2. 用户流程与成功条件

1. **输入与补问**：提取产品、目标人群、使用场景、内容目标、购买阶段和平台。只追问会影响选型或内容策略的信息；具体型号含糊时不能擅自套用相近型号。购买阶段暂不明确但不影响任务时，可以标记未知并说明所用假设。
2. **形成策略**：解释本次优先解决哪个用户问题、卖点如何排序、图片承担什么作用、行动引导指向什么。此时的卖点方向是待检索主题，不是已确认的产品事实。
3. **检索资料与图片**：按型号和任务搜索；搜索为空时分页浏览目录，寻找产品参数目录和对应型号资料。检索到条目不等于读到了原文，更不等于取到了可用图片。
4. **建立事实与图片包**：每条事实保留型号、配置或适用条件、来源定位；每张图保留来源、适用型号的依据和可访问状态。来源不足的信息不进入成稿。
5. **生成图文**：只使用已确认的事实与图片，形成符合平台的标题、导语、正文、图片插入方案和行动引导。
6. **独立核验**：由独立步骤检查生成稿及其依据。规则校验负责数量、引用、版本、敏感表达等确定性条件；语义核验负责事实是否被夸大或遗漏限制条件。不能用生成步骤自己的“检查通过”文字代替实际检查。
7. **修改与导出**：有可修复问题则修改并重验；资料冲突、型号不明或关键素材不足则停止当前成稿，展示具体原因和待确认项。只有当前版本核验通过，才开放“复制成稿”和“导出成稿”。

上述流程与四部分输出来自赛题要求；版本控制、服务端导出门槛及核验分工是本项目的实现设计。[R1，第 5 页]

### 核心不变量

- 产品事实、参数、功能、价格、权益和卖点只能以指定 ima 知识库为依据。用户输入中的宣传要求是请求，不能自动升级为事实来源。
- 使用外部大模型生成文章时，只发送任务所需的最小事实片段和必要的图片信息；不发送 ima 密钥、访问 headers、全库内容或不必要的原文。
- 未证实的价格、补贴、销量、奖项、用户评价、软件测试成绩、个人使用体验不得写入成稿。
- 资料冲突时停止当前成稿并要求人工确认；不静默挑选更有营销优势的一项。人工确认应指向库内有效依据并留下理由，不能凭空补事实。
- 型号/配置、事实适用条件和图片适用范围要一致。文件名或“看起来像这个系列”不足以单独证明图片型号。
- 文案、图片、产品、平台、策略或所用证据发生变化，此前验证立即失效；旧请求迟到的结果不能覆盖新版本。
- 知识库保持只读；不删除、修改或公开传播原始资料。公开项目仓库不得包含凭证、原始接口响应或未经许可的完整素材。[R1，第 5–7、9 页]

## 3. 页面上应当看见什么

界面围绕一次任务组织，避免为内部每个步骤开独立页面。

| 区域 | 应展示的信息 |
| --- | --- |
| 任务输入 | 产品、人群、场景、平台、希望修改的内容，以及必要补问 |
| 连接状态 | 是否配置凭证、目标库是否可读取、最近一次成功核验时间；不要显示完整凭证或内部 ID |
| 内容策略 | 人群问题、内容切入点、卖点顺序、图片用途、平台表达和行动引导 |
| 知识库依据 | 安全来源标题、可理解的定位、对应事实的必要短摘录；支持有权限的受控核查 |
| 图文预览 | 实际图片预览、标题、正文、插入位置、图片说明及来源 |
| 核验结果 | 当前版本的通过项、具体问题、待确认信息；区分规则检查与人工确认 |
| 完成动作 | 核验通过后复制/导出；不足、冲突或改稿后清楚说明为何暂未开放 |

“已识别当前账号”与“凭证能访问目标库”不是同一事实。已审阅的官方知识库接口资料不足以证明存在昵称或当前用户身份查询接口。首版先如实展示凭证和目标库访问状态，并保留客户端同账号确认步骤；账号身份要求是否已满足，需以实际接入证据或组委会认可为准，不能伪造昵称或成功标记。[R1，第 5–7 页；R2]

来源可核查不等于公开原文：评委可看到标题、定位、必要短摘录和受控图片；完整 raw、访问 headers、签名链接、知识库和媒体内部 ID 留在服务端。具体字段边界见 [CONTRACTS.md](CONTRACTS.md)。

## 4. 平台变化要改变实质内容

下面是初始设计方向，后续按真实产品资料和运行结果调整。图片数量是手册要求，其余措辞是本项目策略，不冒充平台官方规则。[R1，第 4–5 页]

| 平台 | 初始结构 | 语气与信息重点 | 图片 | 行动引导 |
| --- | --- | --- | --- | --- |
| 公众号 | 标题、导语、分节解释、限制条件、结尾 | 给出使用问题及选择理由，适合较完整的判断过程 | 2–4 张，分别支持关键段落 | 邀请了解适配场景、咨询或到店体验 |
| 小红书 | 口语化标题、短段、场景要点、话题标签 | 从实际困扰切入；可以提供选购建议，不能伪装真实亲测或用户评价 | 3–6 张，组成有顺序的信息/场景配图 | 引导提出自身需求、进一步了解或咨询 |
| 门店朋友圈 | 短文、一个核心卖点、咨询入口 | 聚焦一个到店体验理由，减少参数堆叠 | 1–3 张，优先能支持该卖点的主图或场景图 | 一个明确的咨询或到店动作；地址、时间、权益无依据时不编造 |

同型号从开学购机改为出差办公，应重排使用问题、卖点和图片用途；同任务换平台，应同时检查结构、语气、图片数量和行动引导。仅替换平台名、字数或 emoji 不算完成。[R1，第 5、9 页]

## 5. 默认技术方案

采用 TypeScript、Next.js App Router 和 Node 服务端，单仓库、单套依赖。页面与服务端处理放在同一项目，先用清楚的模块边界和显式状态流程实现，不增加微服务、消息队列或复杂 Agent 框架。

如现有项目已有适合的技术栈，优先保留；由主控记录与本默认方案的差异，更新运行方法和契约映射。不要为了符合本文重建已有可用工程。

服务端负责 ima 适配、模型调用、事实与图片包、校验、受控素材读取、运行状态和导出门槛。前端只使用明确投影的安全 DTO。原始 provider 响应不得直接作为前端响应，也不得直接当作业务领域模型。

官方 Skill 包已完成静态资料核对，详情由 [IMA_RESEARCH.md](IMA_RESEARCH.md) 记录。开始实现前仍必须验证以下边界：[R2]

- 手册搜索知识库样例使用 `kb_id` / `kb_name`，已审阅官方参考结构使用 `id` / `name`；适配依据真实返回确定，不把二者当成已证明的固定兼容行为。
- 知识条目、文件夹列表及路径面包屑的 ID 结构不同；官方资料中出现 `media_id` 和 `folder_id`，不要盲目交换或构造 ID。
- `get_media_info` 的 `code=0` 可能仍没有可访问 URL；有 URL 时也可能需要 headers 或实际访问失败。笔记类型另有读取分支，不能统一按直链处理。
- 搜索为空、资料不可访问、确实缺少权限和 schema 未识别应是不同结果，不使用一个“连接失败”概括。

## 6. 三个主对话的交付边界

整个项目按三个主对话顺序推进：**真实接入与契约 → 完整实现 → 新上下文独立验收**。每阶段由一个主控负责状态、共享契约与集成，最多三个子线程；需要写代码的 worker 使用独立 worktree。只读调研、检查和日志分析可以委派，但不能假定另一个聊天自动了解本对话决定。

| 阶段 | 必须形成的结果 | 进入下一阶段前的条件 |
| --- | --- | --- |
| 主对话一：真实接入与契约 | 实际账号/权限状态说明、可读取原文、至少一张型号适用范围可证的真实图片、脱敏样本、冻结后的内部契约 | 达到 G1；内部 DTO 与 provider 原始结构明确分开。无法取图或读原文时先解决阻塞 |
| 主对话二：完整实现 | 三平台完整流程、修改重验、核验展示、导出、必要错误处理和真实结果 | 达到 G2、G3；一张图的接入成功不能替代平台完整配图数量 |
| 主对话三：新上下文独立验收 | 从已提交代码和文档重新运行，逐项检查证据，形成缺陷和通过记录 | 达到 G4；不把上一对话自报完成当作验收证据 |

具体并发目录、提交和公共文件责任以根 `AGENTS.md` 为准。`src/contracts/**` 由主控维护，worker 不自行扩展另一套契约。工作树隔离和长期文档交接的官方依据见 [R3]、[R4]。

## 7. 完成的定义

首次真实接入门槛是“原文可读＋一张型号可证图片可用”，它只证明技术路径成立。正式可用还需要：满足所选平台全部图片数量、事实可追溯、场景与平台有实质变化、异常正确处理、改稿重新核验、可导出，以及真实运行证据。

复赛材料至少包含 3 组运行结果，覆盖至少 2 类业务场景及 2 个平台，并注明资料和图片来源；提交真实流程录屏，连续展示一次完整运行并补充换场景或换平台。GitHub、魔搭页面、说明书和视频描述要与实际功能一致。[R1，第 2、8 页]

验收门槛、用例和当前未执行状态统一记录在 [ACCEPTANCE.md](ACCEPTANCE.md)。
