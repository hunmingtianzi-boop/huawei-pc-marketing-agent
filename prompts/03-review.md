# 第三轮主对话：独立验收、修复与参赛材料

你是本阶段主控与最终质量负责人。用新上下文检查当前仓库，不预设前一轮报告正确。先读取 AGENTS.md、docs/STATUS.md、docs/DECISIONS.md、docs/SPEC.md、docs/CONTRACTS.md、docs/ACCEPTANCE.md 和实际实现。

## 开始

核对稳定提交、工作区状态、运行方式、提示词、真实接入证据及尚未解决项。按 README 从当前代码启动应用，确认没有依赖隐藏的人工步骤。

在代码暂不被改动的版本上，最多同时派三个只读 reviewer 子任务：

1. 接入与事实：ima 来源、型号/配置/限制条件、目录回退、图片可用与来源、数据冲突、凭证边界。
2. 场景与成稿：澄清、人群与平台差异、图数、虚构事实/体验、临时修改以及重新核验。
3. 运行与交付：README 可复现、构建和异常行为、页面关键路径、最终输出、提交材料与实际功能一致性。

每个任务给出基准提交和验收条目。检查真实代码与可复现行为，返回问题严重性、证据文件/位置、复现步骤和建议；默认不改源码。不能仅列想象中的风险作为缺陷。

## 核对与修复

等待评审后，主控验证问题并按影响修复。必要时分配单一写入者；若多个修复可独立并行，仍用不同 worktree。复验针对具体改动及其影响，避免无限扩大测试。

产品陈述的来源/数值/单位、图片来源、冲突停稿、修改后重验、三平台行为是关键项。把核验规则实现为真实检查，不能靠模型输出“通过”或简单关键词存在判定全部完成。

## 真实案例与录屏

按 ACCEPTANCE 执行并记录结果。说明书至少收录三组真实运行结果，覆盖两类业务场景和两个平台；工程验证同时覆盖首版三个核心平台。

建议连续演示序列：缺失信息任务→确认型号并生成→只换人群→只换平台→加入无依据补贴或混淆型号→展示拦截/修订→导出。

有工具能力时录制一次完整真实运行，补充切换结果。若当前客户端无法录屏，完成可直接执行的演示脚本并准确标为录屏待补，不伪造视频或假称已完成。必要剪辑不掩盖代写、固定结果和人工替换。

干扰样例可以是明确标注的合成测试数据；不要修改举办方知识库。回放不能伪装为实时连接。

## 提交材料

完善源码、README、依赖、安装和运行方法、系统提示词、部署步骤、已知限制、作品说明书与演示说明；为 GitHub 和魔搭准备真实且相互一致的信息。

若用户尚未授权公开发布，先完成可审阅的内容与部署配置，分别列出待发布动作；已有明确授权时按该授权执行。不能因尚未发布而停下本地工作，也不能编造提交链接或“评审可访问”结论。

检查公开仓库与材料不含 API Key、Client ID、受限原件、完整知识库镜像或敏感访问头。证据展示保留比赛需要的安全出处及必要短摘录。

## 最后交接

更新 STATUS，逐项列明 PASS / BLOCKED / FAIL，引用实际验证结果与对应提交。说明真实已实现的能力、尚未通过的条件、提交文件位置和唯一下一步。不能保证比赛得分或晋级。
